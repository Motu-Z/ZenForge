## 二、SmoothSortPanel 逐项审查

### 2.1 【高】滚动抑制可能永久失效 —— 已修

**原实现**

```csharp
private void OnLoaded(object sender, RoutedEventArgs e)
{
    if (_scrollHooked) return;
    ScrollViewer? host = FindScrollHost();
    if (host == null)
        return;                      // ← 找不到就永久放弃
    host.ScrollChanged += OnScrollChanged;
    _scrollHooked = true;
}
```

**问题**：`ItemsPanel` 是 `ItemsControl` 首次布局时才实例化的，`Loaded` 触发的那一刻它的祖先链可能还没搭完（`ScrollViewer` 尚未成为父级）。一旦这一次没找到，面板就永久停留在「没订阅」状态 —— 于是滚动期间不做抑制，行追着滚动条跑。

这条尤其讽刺：**滚动抑制正是这个面板存在的唯一理由**，失效后它退化成了一个「在滚动时制造怪异动画」的面板。

**修法**：找不到时排一次 `Dispatcher.BeginInvoke(..., DispatcherPriority.Loaded)` 重试 —— 那时可视树已稳定，代价只有一帧。用 `_retryScheduled` 保证重复 `Loaded` 不会堆积委托。

### 2.2 【中】位移上限写死 480px —— 已修

`MaxSlide = 480` 的语义是「超过一屏就不补间」，但**一屏不是常数**：它随窗口大小和高 DPI 变化。1440p 窗口 + 150% 缩放下列表视口能到 900+ 逻辑像素，此时 480 会拦掉正常的换位，功能变成时灵时不灵 —— 而「时灵时不灵」比「完全没有」更难诊断。

**修法**：改为 `SlideLimit = ViewportHeight × 0.9`，视口高度从 `ScrollChanged` 里跟着更新（窗口 resize 也不脱节）；拿不到视口时才用 480 兜底。

### 2.3 【低】ScrollViewer 强引用面板 —— 已修

`ScrollViewer` 通过 `ScrollChanged` 强引用面板。同生共死时无所谓，但换页、或 `ItemsControl` 换 `ItemsPanel` 而 `ScrollViewer` 仍存活时，这个引用会把面板多留一会儿，连带那张 `ConditionalWeakTable`。

**修法**：加 `Unloaded` 钩子解绑、状态归零；下次 `Loaded` 重新挂。

### 2.4 【中】`RequestSmooth` 只清第一个面板 —— 已修

进程页有两个列表（全部 / 已绑定），各有一份 `ItemsPanel`。原实现递归找到**第一个**就返回，而「第一个」取决于 XAML 声明顺序，未必是此刻显示的那个：点表头排序时，用户看到的那个列表没有过渡，隐藏的那个白白被清了一次。

**修法**：改为清子树里**每一个**面板。两个列表互斥显示，全清没有副作用；递归只在「点了列头」时发生一次，不值得为它维护引用。

### 2.5 布局死循环 —— 结论：不存在

审查时按「什么会让 `Arrange` 递归」逐条排查：

1. `TrackPositions()` 在 `base.ArrangeOverride()` **返回之后**调用，此时容器已稳定，不会在基类布局中途插入操作。
2. `Slide()` 修改的是 **`RenderTransform`**，不是 `LayoutTransform`。`RenderTransform` 不参与 `Measure`/`Arrange`，只影响渲染 —— 改它不会让父面板重新布局。（这是本条结论的关键：换成 `LayoutTransform` 就会立刻死循环。）
3. `BeginAnimation` 启动的动画时钟每帧改 `RenderTransform`，触发的是**渲染**失效，不触发 `Arrange`。
4. `Reset()` 里设 `tt.X/Y = 0` 同理。
5. `VisualTreeHelper.GetOffset(child)` 读的是 `Visual` 的布局偏移，不含 `RenderTransform`，因此每次 `Arrange` 读到的基准值稳定，不会出现「读了被动画改过的值」这种自激。

**结论**：`Arrange → 改 RenderTransform → 渲染 → （不回到 Arrange）`，无回路。

### 2.6 内存泄漏 —— 结论：无泄漏路径

| 可能的泄漏点 | 判定 |
|---|---|
| 位置记录以容器为键 | ✅ 用 `ConditionalWeakTable`，键是**弱引用**，容器被虚拟化回收时条目自动消失，不需要任何清理逻辑。若用普通 `Dictionary` 就是「滚一圈泄漏一屏」 |
| `Slot._data` 持有 `DataContext` | ✅ 是 `WeakReference`，不延长数据存活 |
| 动画时钟常驻 | ✅ `FillBehavior.Stop`，时钟跑完即释放，不留 `HoldEnd` 长期挂在行上；`Stop` 的语义也保证容器被回收复用时不带残留偏移 |
| `CubicEase` / `DoubleAnimation` 每次 new | ✅ 用完即弃，无引用链 |
| ScrollViewer 事件强引用面板 | ⚠️ **原为泄漏点**，已在 §2.3 修掉 |

## 三、线程安全审查

### 3.1 全局异常限流 —— 结论：无并发漏洞，但有一处慢泄漏（已修）

三条通道的调用关系先厘清：

| 通道 | 是否调用 `HandleUiException` | 线程 |
|---|---|---|
| `DispatcherUnhandledException` | 是 | UI 线程（唯一） |
| `AppDomain.UnhandledException` | 否（只走自己的落盘分支） | 任意 |
| `TaskScheduler.UnobservedTaskException` | 否（同上） | 任意 |

因此：

- `_signatureTotal` 被**三条通道并发**访问 → 已有 `lock` 保护 ✅ 正确。
- `_signatureDialogCount`、`_lastExceptionSignature`、`_repeatedCount` 只在 `HandleUiException` 内访问，而它**只由 UI 线程通道进入** → 单线程，无需加锁 ✅ 正确。（这一点容易被误判成漏洞，实际是安全的。）

**唯一的真问题**：`_signatureTotal` 有「超 256 条整表清空」的兜底，`_signatureDialogCount` 没有。而签名是「类型 + 最内层消息」，消息里常带变化的值（进程名、路径、句柄号），理论上是**无界**的 —— 一个长期驻留的进程攒下几万条签名，就是一条谁也不会去查的慢泄漏。

**修法**：两处统一用 `MaxTrackedSignatures = 256`（顺带把 `_signatureTotal` 里的字面量也换成常量）。清空最多让某个老签名重新获得一次弹框机会，不影响任何限流语义。

> `Paused` / `Verbose` 是普通 `static bool`，跨线程无 `volatile`。判定：**可接受**，不予修改。x86/x64 上对齐的 `bool` 读写是原子的，而这两个开关的语义本就容忍「晚一拍生效」——为它们加 volatile 只会让读代码的人误以为这里存在需要严格时序的契约。

### 3.2 日志内存截断 —— 结论：无漏洞，修掉一处清空竞态

确认安全的部分：

- `EntriesInternal` 的所有写都在 `EntriesGate` 内；UI 模式下写全被封送到 UI 线程而天然串行，静默模式下锁是唯一保护 ✅
- `Snapshot()` 在锁内 `ToArray()`，出去后副本归调用方，不与写入路径争锁 ✅
- `EnqueueFile` 的 `FileSignal.Set()` 放在 `FileGate` **外面**，避免在锁内触发上下文切换 ✅
- `ClearMemory` 用 `Monitor.TryEnter(100ms)` 而非 `lock`：拿不到锁时宁可放弃这次清空并记一笔，也不让 UI 线程陪着一起等 ✅
- `AutoResetEvent` 取代 `ManualResetEventSlim`，堵住「Set 落在 Wait 已返回、Reset 未执行的缝里」✅

**修掉的竞态（§0 第 5 项）**：原 `Clear()` 把「清队列 + 推进代号」放在 `ClearMemory()` 里，而后台线程走的是 `UiContext.Post` —— **Post 是异步的**。于是「后台删文件的任务」可能比「推进代号」先跑完，写盘线程趁这个窗口把队列里那批旧日志写进刚被删掉的文件：用户点的是「清空」，看到的是旧日志原封不动回来了。

**修法**：代号与队列的推进提到 `Clear()` 的**调用方线程**上当场完成，再去做内存清空与删文件。

### 3.3 v1.1.x 新增代码的线程边界

`ScenarioService.Notify` 在入口做一次 `SynchronizationContext` 封送（后台线程进来就 `Post` 回 UI 再走），责任放在「把调用带到别的线程」的那一侧 ✅。后续新增的 `ScenarioMonitor.Evaluate` 跑在 `Timer` 线程上，同样经由这条路径封送 ✅。

## 五、v1.1.x 实装部分的新增审查

（这一节是针对本轮新写入代码的补充审查，与 rc1 无关，但同属「交付前必须自查」的范畴。）

### 5.1 【高】场景切换短路比错了对象 —— 已修

```csharp
// 原：比的是「上次场景自己切到了哪」
if (target == null || target == LastAppliedProfileId) return;
```

「上次是场景切的」不等于「现在还是那套」—— 中间用户可能手动切过。**现场**：插电时场景切到「性能」，用户手动切到「静音」，再拔插一次电源，场景一看 `target` 和上次一样就跳过了，于是用户的手动选择被无声地保留下来，而他期待的是场景重新接管。

**修法**：改比 `ProfileService.ActiveId`（无论谁切的都算数），`LastAppliedProfileId` 降级为纯显示用途。

### 5.2 后台零占用：新增监听的专门审查

新增的三个常驻输入源都按「不启用 = 不订阅 + 无活动定时器」实现：

| 输入源 | 静默期成本 | 兑现方式 |
|---|---|---|
| 进程事件 | 0 | 只在存在**进程类规则**时才订阅 `ProcessWatcher.ProcessSetChanged`；无此类规则时不挂 |
| 电源（`SystemEvents`） | 0 | 只在存在**电源类规则**时订阅；OS 事件，无轮询 |
| 电源（轮询兜底） | 0 | `PowerStatusWatcher.Stop()` **真的 Dispose 掉 Timer**，不是只置标志位；且状态没翻转时不广播 |
| 防抖定时器 | 0 | `Timer` 用 `dueTime=Infinite` + `period=Infinite`，只在被 `Schedule` 推一把时醒一次 |

**降级轮询模式的额外处理**：`ProcessWatcher.ScanOnce` 每 3 秒一轮，若无条件广播，订阅方会跟着每 3 秒取一次全量进程名单（几百次 `OpenProcess`，比轮询本身还贵）。改为**只在存活 PID 集合真的变了时**才广播 —— `SetEquals` 是 O(n) 整数比较，比取名单便宜三个数量级。

### 5.3 自检不下发硬件

`ScenarioSelfCheck` 刻意不调 `TuningApplyService`、不写 SMU、不改进程绑核：跑一次自检把用户的负压值改掉，代价与收益完全不成比例。硬件下发那一段只能靠真机验收。

## 七、未修项与理由

| 项 | 理由 |
|---|---|
| 场景规则编辑器 | 本轮纪律要求**不改 XAML / UI**，编辑器必然是界面工作，留给下轮 |
| 调校下发失败的回滚 | 需要「部分写成功」的回滚顺序（先 FMax 后 CO）的**实测依据**，不猜。已在 `ProfileService.Apply` 注释里标出 |

| 视觉与 DPI 观感 | **无 Windows 运行环境，无法验收**。平滑动画的观感、`UiTextOptions` 的实际渲染效果需真机确认 |
